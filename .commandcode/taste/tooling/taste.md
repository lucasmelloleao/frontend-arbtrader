# Taste — Tooling & Workflow

- Maintains a multi-host AI agent setup (Claude Code, Command Code, Codex, Cursor) in the same repo and expects agent configuration to stay in parity across hosts — when a new host is added, its config should incorporate the content from the canonical source (skills, slash commands, hooks, docs) rather than minimal stubs ("incorpore" = full incorporation). Confidence: 0.6
- Prefers agent enforcement logic centralized once in host-agnostic shared scripts (e.g., `tooling/agent-hooks/`) with per-host config files pointing at them, and wants new host surfaces added to the enforcement gates/tests and CODEOWNERS so changes can't silently disable the setup. Confidence: 0.6
- Uses `bun run verify` as the canonical full quality gate (lint + typecheck + format + knip + tests + guards) and expects it to be green before finishing a task; runs individual checks (`lint`, `typecheck`, `fmt:check`, `knip`) iteratively while fixing violations, and runs `bun run verify:fast` as a mid-task quick gate before the final full `verify` at the end. Confidence: 0.8
- Has no admin rights on their machine — tooling installs and setup must work in user scope (user-level binaries, PATH via user environment variable) without elevation. Confidence: 0.9
- Develops on Windows and expects repo tooling/scripts to be cross-platform: no dependence on Unix-only binaries (e.g., `grep`) and explicit handling of path separator differences (e.g., `Bun.Glob` returning `\` on Windows). Confidence: 0.7
- Wants `.env.local` (and `.env` setup in general) created from the repo's `.env.example` placeholders rather than invented values, and expects production builds to be runnable against that placeholder config. Confidence: 0.5
- When the local `openapi.yaml` and the backend's published swagger diverge, diagnoses it as a stale backend deployment: re-fetches the live spec (e.g., from `swagger-ui-init.js`) and diffs it against the local copy to confirm which implementation the server is actually running — the published swagger keeps describing the old behavior until the new backend code ships, so the fix is "publicar/deployar a nova implementação do backend" and the local spec already reflecting the new behavior is not proof the server runs it. User reaffirms this when mid-deployment ("o servidor ainda deve esta publicando"), so the agent tests the live endpoint directly to determine the actual running version instead of concluding from the stale published spec. Reaffirmed when the user updates the contract and the published swagger still lacks the new fields — the agent confirms the published spec is stale and reports the backend still needs to ship. Confidence: 0.8
- When the backend publishes its swagger to a live URL, treats that published spec as the authority for "direcionar as chamadas" (directing which endpoints/payloads to call) — after publishing, the user points at the URL ("agora o swager esta publicado em ... utilize-se para direcionar as chamadas de acordo") and expects the agent to fetch/consult the published OpenAPI spec rather than relying only on the local `docs/api/openapi.yaml` copy. The user'll correct the URL if the agent guesses the path wrong (gave `/api-docs`, user corrected to `/docs/`); the live spec is served via Swagger UI at `<host>/docs/` with the spec embedded in `swagger-ui-init.js`. The user also explicitly asks the agent to verify that the local spec is "de acordo" (in agreement) with the published one — prompting the agent to compare the embedded published spec against the local `openapi.yaml` and confirm parity rather than trusting the local copy blindly. When the backend starts returning new metrics (e.g., APR, entry/exit volumes for closed trades), the user expects the frontend screen to be adjusted to display them and expects the agent to consult the published swagger to confirm exactly what the API now returns before wiring it up — not assume from the old local copy. Confidence: 0.9
- Prefers downloading the backend's full OpenAPI spec into the project and interpreting it locally over repeatedly probing the live server — after asking the agent to consult the published swagger, the user suggested "baixar o swager inteiro para o projeto e interpretar local" so the working copy lives in the repo (then kept in parity with the published spec) instead of depending on repeated live fetches/HTTP probes against the host. Confidence: 0.6
- When migrating a legacy app, explicitly authorizes inspecting the legacy `.env` files to source necessary env vars, trusting the agent to reuse only what fits the new architecture and to not copy real secrets into the new project. Confidence: 0.5
- Expects runtime configuration (backend API base URLs, etc.) to be resolved from `.env.local` environment variables, not hardcoded in source — placeholder domains like `api.example.com` belong only in docs/examples and test fixtures, never in actual runtime call paths. Confidence: 0.8
- When `.env.local` values change, expects the dev server to be restarted (or `.next` cleared) so the browser bundle is recompiled with the new `NEXT_PUBLIC_*` values — editing env files alone doesn't update the inlined values in already-built chunks, and a stale URL in the running bundle is treated as a bug to fix. Confidence: 0.7
- Environment has `NODE_ENV=production` set globally (observed in dev server boot logs) — dev-mode assumptions don't hold; configuration logic should gate on actual env values (e.g., presence of `INTERNAL_API_URL`) rather than `NODE_ENV` checks. Confidence: 0.8
- Diagnoses frontend/backend mismatches empirically: probes what the backend actually returns (curl/PowerShell against the real port, trying the exact request shapes the frontend sends) before assuming the response contract matches the boilerplate, rather than guessing from code. Confirms connectivity by checking that the configured port responds (e.g., a 404 on the root of a remote host is treated as the server being up, since the REST backend serves under `/api/*`). When a login/API call returns 404, distinguishes a failing rewrite from a wrong endpoint by hitting the backend directly and probing candidate paths (e.g., `/api/v1/login` vs `/auth/login`) and ports to map what the remote server actually exposes. Confidence: 0.7
- Expects YAML/OpenAPI spec files to be syntactically valid so they pass the format gate (`bun run verify:fast` runs oxfmt over repo files and fails on malformed YAML, e.g., an unquoted `:` inside a description value) — runs the gate after creating/editing spec files and fixes syntax errors caught by it. Confidence: 0.6
- When a lint rule would block a legitimate integration need (e.g., `no-underscore-dangle` flagging the Mongo `_id` field read at the API boundary), prefers scoped config allowances (`.oxlintrc.json` rule with `allow: ["_id"]` plus a comment explaining the boundary) over renaming, wrapping, or disabling the whole rule. Confidence: 0.6
- When creating reusable schema helpers that normalize at the API boundary (e.g., a valibot `refIdSchema` handling string/null/populated-object ref ids), keeps them colocated in the feature's schema module near the schemas that use them, rather than a shared helper module — and removes unused imports introduced while iterating on the helper. Confidence: 0.5
- Treats the repo's OpenAPI/Swagger contract (`docs/api/openapi.yaml`) as the canonical source of truth for what the backend exposes. When a frontend need can't be satisfied by the current contract, waits for (or asks for) the backend/contract to be updated and then re-analyzes the contract to confirm the capability before proceeding — the user signals contract updates with messages like "atualizei o contrato swagger, analise, agora o backend tem o que precisa" and expects the agent to re-examine the spec (not assume the old state) once it changes. Reinforced when the user explicitly prompts again ("veja novamente, faltou saltar o arquivo") after the agent concludes from a stale read — the agent must always re-read the file when the user hints it may have changed. Reaffirmed when the user introduced a new dashboard report contract by editing the local spec and pointing at it directly ("de acordo com o swager PerpArbAuditExchangeResponse recem criado"): the agent re-reads the local `openapi.yaml` for the new endpoint/schema and checks whether the published swagger already has it (it did not), then implements the feature from the local contract. Confidence: 0.9
- Verifies endpoint existence and backend state by diffing the published swagger against the local spec (e.g., path/schema counts like "24 paths/51 schemas vs 23/50") to detect that the backend has been redeployed with new endpoints — when a runtime call fails with the transport fallback error and the live spec now contains the endpoint, concludes the published route exists (confirmed also by a direct unauthenticated probe returning 401) and the failure is elsewhere, e.g., a per-request timeout on heavy report endpoints. Confidence: 0.6
- Treats the actual runtime payload as ground truth over the declared contract type: when a valibot error ("Expected number but received \"USDT\"") shows the backend returns a currency code as a string while both the published swagger and local `openapi.yaml` typed `feeCurrency` as `number` (a backend typo), corrects the schema to `optional(nullable(string()))`, fixes the local `openapi.yaml` to `type: string` in parity, and adjusts the render to handle the `string | null` union — the spec is corrected to match what the backend really returns, not the other way around. Confidence: 0.4
- Deploys the frontend to Vercel and expects the repo toolchain to be Vercel-build-compatible: the `packageManager` field in `package.json` must pin a stable Bun version that exists on GitHub Releases (e.g., `bun@1.4.0`, matching the local install and the lockfile) — Vercel's `setup-bun` reads that field and downloads the exact binary, so a canary version that isn't published there fails the deploy build with a 404 (user pasted the Vercel CI error and stated "quero gerar meu front na vercel"). Confidence: 0.6
